# F3-19 — Contexto previo de revisión y filtración temporal

**Fecha:** 2026-11-06. **Base:** `8c03c02cfac0ca73df400455ff6c319a6315c3e2`. **Alcance:** código F3-18 y prueba local sintética; proveedores reales, API y máquina remota `NOT_RUN`.

## Pregunta y diagnóstico

**¿Podemos demostrar exactamente qué contexto recibió cada revisor antes de actualizar perfiles e historiales?** Para la *proyección canónica de la solicitud estructurada local* sí: los tres bytestrings se reconstruyeron después de aplicar la adjudicación y coincidieron byte por byte y por SHA-256. Para un payload histórico que incluya perfiles o para el texto exacto entregado a una UI/proveedor, **no**: no existe tal payload operacional conservado. Los manifiestos de aplicación guardan hashes de los perfiles anteriores, pero no su contenido; el prompt literal del fake procede de `FakeSiteReviewerAdapter.prompt` y tampoco se conserva en el set v2. Esta ausencia se informa `HISTORICAL_CONTEXT_UNAVAILABLE`, nunca se rellena con el estado actual.

**Diagnóstico B — estimación retrospectiva con instantánea actual**, con un límite explícito de preparación para futuras APIs. El flujo de revisión F3-18 no lee perfiles ni historiales al construir `ReviewerExecutionRequest` ni al preparar el prompt fake. Por ello no se demostró filtración temporal operacional de esos archivos en el revisor actual. La adjudicación sí los lee después de la barrera 3/3. No se creó persistencia nueva ni se modificaron orquestador, contratos v2 o adjudicación. D-040 ya reconoce que la preparación del contexto acumulado para revisores reales es futura; esta auditoría confirma ese contrato y no requiere otra decisión arquitectónica.

## Arquitectura y orden causal comprobados

1. O-01 inspecciona el statement pendiente y el run. O-02 toma `WorkflowLease`, relee el plan dos veces y calcula una huella de `statements`, `runs`, `review_cases`, `feedback` y `profiles` ([coordinador](../automation/workflow_coordinator.py), `_precondition_fingerprint`, líneas 369–387). La huella detecta cambios entre preparación y ejecución, pero **no** es copia recuperable del contenido.
2. El vertical carga declaración y tres outputs del run seleccionado con `inspect_review_inputs`, exige `selected_run_id == plan.run_id` y crea `ReviewerExecutionRequest(plan, inputs, task, attempt)` ([vertical](../automation/review/vertical_flow.py), líneas 385–463). `ReviewInputValidation` contiene statement, outputs y run, sin perfil, historial ni prompt ([loader](../automation/review/input_loader.py)). Los outputs del statement actual son legítimos; el índice por sí solo no acredita orden causal entre runs.
3. El revisor determinista usa `statement_index` y marcador sintético; `FakeSiteReviewerAdapter` prepara `self.prompt` con slot e identidades, sin texto del statement, outputs, perfiles ni historiales ([adaptador](../automation/review/fake_site_adapter.py), líneas 88–97). No hay SDK ni payload real de ChatGPT/Gemini/Grok. La solicitud manual durable guarda solo identidades, no el contexto ([manual](../automation/review/manual_supervisor.py), `ManualRequest`).
4. `CompleteReviewResult` exige 1 revisión principal, 3 propuestas de historial y 3 de perfil. El publicador v2 conserva siete artefactos, hashes canónicos, run e intento ([escritor](../automation/review/review_storage.py), líneas 280–323). O-01 no habilita adjudicación hasta 3/3.
5. **Después** de confirmar los tres sets, `_build_bundle_request` lee los perfiles actuales ([adjudicación](../automation/review/synthetic_adjudication.py), líneas 895–908). `commit_adjudication_bundle` lee historiales y perfiles, valida transiciones y calcula siete `source_sha256` ([aplicación](../automation/review/adjudication_storage.py), líneas 1132–1159). El manifiesto v2 conserva hashes de origen/destino, run e intentos; `prepared/` conserva los **destinos nuevos**, no los perfiles anteriores (líneas 435–464 y 540–555). La aplicación reemplaza destinos individualmente, comprueba hashes, permite recuperación e idempotencia y publica evidencia final. No es una transacción multiarchivo.

Contexto legítimo de una futura revisión: declaración actual, tres outputs alineados, instrucciones exactas, metadatos y, si la política lo decide, historiales/perfiles válidos *antes* de esa revisión. Adjudicación actual, propuestas ya aplicadas, perfiles/historiales posteriores y resultados futuros quedan fuera. El flujo local fake actual nunca ensambla ese contexto ampliado.

## Experimento reproducible

`tests/test_review_context_reproducibility.py` crea en `tmp_path` statement 010, tres outputs de `run-a`, tres perfiles con diez outputs anteriores y tres historiales con índices 000–009. `CapturingReviewer` captura, antes de toda aplicación, la representación UTF-8 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))` de la **proyección declarada** `f3-19-request-projection-v1`: run, índice, revisor, task, attempt, número de intento, statement y tres outputs. Calcula SHA-256 de esos bytes. Esta proyección es explícita y comprobable; **no** se presenta como prompt de transporte.

`run_synthetic_range` ejecuta tres revisores deterministas, barrera 3/3, publicación v2, adjudicación, aplicación de seis destinos y completitud. Después, el test relee los inputs y los sets activos, verifica run, tarea e intento contra ambos manifiestos, vuelve a serializar y compara `rebuilt == captured` y ambos SHA-256 para los tres revisores: **PASS**. El replay produce cero pasos: **PASS**. Los hashes de preimagen de los seis archivos coinciden con la captura previa, mientras los bytes posteriores son distintos: **PASS**. Ninguno de los tres hashes de perfil anterior corresponde a un archivo en el almacén de aplicación; un hash aislado no recupera esos bytes: **UNAVAILABLE**. El estado inicial solo se conoce porque el test lo capturó deliberadamente fuera del almacén operacional.

La alteración sintética `FUTURE_LEAK_MARKER` en un perfil, incluso después de preparar una tarea manual y construir su solicitud, no aparece en la solicitud al fake: **PASS**. Una mutación posterior de historial tampoco entra en esa solicitud: **PASS**. Cambiar bytes de perfil o historial después de preparar la expectativa O-02 produce `STALE_PLAN` antes de llamar al adaptador: **PASS**. Esto demuestra protección para el *revisor local actual* y cambios observados antes de la revalidación; no demuestra aislamiento de una futura construcción de payload con perfiles ni atomicidad frente a escritores externos hostiles.

La lectura read-only de `tools/estimate_review_tokens.py` y de `reports/token_estimation/{reconciliation_000_009.md,summary.md,statements_000_009.csv}` se hizo en el checkout OneDrive, no en este commit F3-18. El script carga **una vez** los perfiles actuales de `config/profiles/` (líneas 107–108) y los reutiliza en cada índice (línea 151); filtra historiales por `output < index` (línea 143). Las etiquetas numéricas del CSV son `PROXY_CONTEXT_AND_TOKENIZER`; el informe de conciliación explica expresamente la limitación. El script no se modifica porque es un archivo previo no versionado de otro checkout y ya declara el límite; la estrategia correcta para esa serie es conservar la etiqueta de snapshot actual.

## Riesgos y siguiente integración

Antes de integrar una API o un revisor web real, definir el payload y serialización exactos y fijarlos **antes del envío** con run, statement, revisor, tarea, intento, prompt/version, identidades y hashes de outputs y versiones y contenido recuperable de perfiles/historiales previos. Reutilizar el almacenamiento JSON/JSONL y manifiestos existentes si se aprueba el diseño; una referencia por hash requiere contenido inmutable recuperable. Revalidar bajo lease antes del envío y tratar envíos inciertos mediante conciliación, sin retransmisión automática. Probar mutación posterior, reinicio, dos tareas concurrentes y reconstrucción exacta desde proceso nuevo. No atribuir tiempos causales a partir de `statement_index` únicamente. Mantener el No-Go de proveedores reales de D-051 hasta resolver permisos, privacidad y procedencia.

Las fuentes operacionales 000–009 no se reabrieron ni se usaron para inferencia. No se inventaron snapshots. El experimento solo demuestra propiedades de un fixture sintético local y de los contratos F3-18.
