# Registro de decisiones (ADR ligero)

## D-001 — Enfoque local
**Fecha:** 2026-10-10
**Decisión:** Python es el orquestador; Playwright es la capa de navegador, sin depender de n8n.
**Motivo:** control local y modularidad.
**Consecuencia:** deben implementarse persistencia, reintentos y observabilidad.

## D-002 — Interfaces web como preferencia
**Fecha:** 2026-10-10
**Decisión:** priorizar sesiones web frente a API de pago, sin asumir permiso para automatizar plataformas de terceros.
**Consecuencia:** cada adaptador documentará capacidades autorizadas; si una operación no está permitida, se deshabilita y puede quedar un paso manual trazable.

## D-003 — Contexto de Codex
**Fecha:** 2026-10-10
**Decisión:** `AGENTS.md` en raíz como instrucción automática; `context/` guarda metas, arquitectura, decisiones, avances y prompts.
**Consecuencia:** Codex debe leer documentos explícitamente; no se confunde un archivo Markdown con memoria automática.

## D-004 — Investigación reproducible
**Fecha:** 2026-10-10
**Decisión:** rúbricas versionadas, validación de feedback, separación por caso y control humano de perfiles.
**Consecuencia:** no marcar una mejora sin evidencia ni entrenar/evaluar sobre mismos casos derivados.

## D-005 — Perfiles persistentes fuera del repositorio y bloqueo exclusivo
**Fecha:** 2026-10-10
**Contexto:** el checkout está dentro de OneDrive y un perfil Chromium puede contener cookies, credenciales y archivos volátiles que no deben sincronizarse ni abrirse concurrentemente.
**Opciones:** guardar perfiles bajo el repositorio; usar contextos efímeros; exigir una raíz externa explícita con bloqueo por perfil.
**Decisión:** `BrowserManager` recibe una raíz de perfiles explícita, crea un subdirectorio por nombre y mantiene un bloqueo de sistema operativo mientras el contexto persistente está abierto.
**Consecuencias:** el llamador debe configurar una ruta local fuera de OneDrive; dos procesos no pueden compartir el mismo perfil; `.gitignore` actúa como defensa adicional, no como ubicación recomendada. El bloqueo usa `fcntl` en POSIX y `msvcrt` en Windows; solo macOS se ha validado efectivamente.
**Evidencia:** `tests/test_browser_manager.py` valida ciclo de vida, exclusividad y liberación tras un fallo; el smoke local abre Chromium con datos sintéticos.

## D-006 — SessionManager coordina proveedores sin asumir capacidades web
**Fecha:** 2026-10-10
**Contexto:** la fase 1 requiere sesiones persistentes e independientes, pero aún no existe autorización ni matriz de capacidades para navegar, autenticar, enviar o extraer contenido de plataformas externas.
**Opciones:** incorporar navegación en el administrador de sesiones; compartir un contexto; coordinar un `BrowserManager` persistente por proveedor sin lógica de plataforma.
**Decisión:** `SessionManager` acepta únicamente `chatgpt`, `gemini` y `grok` como nombres de fronteras de aislamiento, crea un `BrowserManager` por proveedor y delega completamente apertura, cierre, persistencia y bloqueo. La raíz se configura con `POLICE_BENCH_BROWSER_PROFILE_ROOT` o usa el directorio de estado del usuario apropiado para macOS, Linux o Windows; rechaza componentes conocidos de carpetas sincronizadas.
**Consecuencias:** las sesiones no comparten almacenamiento; cerrar o fallar un proveedor no impide intentar cerrar los demás; los adaptadores y permisos siguen pendientes. La detección de carpetas sincronizadas es una defensa basada en nombres conocidos y no sustituye la revisión de una ruta personalizada.
**Evidencia:** pruebas con página HTTP sintética en `127.0.0.1` verifican aislamiento y persistencia de `localStorage`; pruebas adicionales verifican reapertura tras cierre inesperado y bloqueo del mismo perfil desde otro proceso.

## D-007 — Desarrollo local y ejecución remota con dependencias separadas
**Fecha:** 2026-10-10
**Contexto:** Playwright se desarrolla en macOS, pero la ejecución final ocurrirá en una máquina remota que también contiene inferencia y cuyas características aún no han sido auditadas. Instalar el conjunto completo de inferencia en el entorno local de navegador introduce acoplamiento y riesgo innecesarios.
**Opciones:** un único archivo y entorno para inferencia, automatización y pruebas; separar dependencias y entornos conservando el archivo histórico de inferencia.
**Decisión:** preservar `requirements.txt`; declarar el runtime web en `requirements-automation.txt` y las herramientas locales en `requirements-dev.txt`. Usar `.venv311` localmente y un entorno dedicado distinto en el servidor. Transferir código mediante Git, nunca perfiles o secretos.
**Consecuencias:** la capa de navegador puede probarse sin instalar modelos; el servidor requiere auditoría antes de instalar Chromium o dependencias; la validación remota permanece `NOT_RUN`.
**Evidencia:** suite local completa con Python 3.11.17, Playwright 1.60.0 y pytest 9.1.1: 17 pruebas aprobadas, incluidas las tres pruebas Chromium opt-in y la regresión de aperturas concurrentes.

## D-008 — Tipo de tarea separado del ciclo de vida e identidad de repetición
**Fecha:** 2026-10-10
**Contexto:** la arquitectura propuesta usaba nombres de etapas como estados, mientras que el entregable 2.1 requiere tipos de tarea independientes y un ciclo de vida común. También es necesario distinguir un reintento técnico de una nueva repetición experimental.
**Opciones:** mezclar etapa y ejecución en un único enum; crear una tarea nueva por cada intento; separar tipo, estado, intento y repetición explícita.
**Decisión:** `TaskType` identifica `generation`, `evaluation`, `feedback`, `profile_optimization` y `dataset_preparation`; `TaskStatus` identifica el ciclo de vida. `FAILED`, `COMPLETED` y `CANCELLED` son terminales. Un fallo recuperable usa `RUNNING → RETRY_PENDING → RUNNING` y conserva `task_id`; cada ejecución usa `attempt_id` y `attempt_number`. Una repetición experimental nueva cambia `experimental_repetition`, que forma parte de la clave de deduplicación junto con experimento, caso, tipo, proveedor, modelo, versiones e iteración.
**Consecuencias:** la persistencia futura puede aplicar unicidad a la clave lógica sin confundir reintentos con réplicas del experimento. Las tareas de generación exigen caso, proveedor, modelo y versión de prompt; evaluación y feedback exigen caso; optimización de perfil exige proveedor, modelo y versión de perfil; preparación de dataset no exige esos campos opcionales. La política que decide cuántos reintentos ejecutar sigue pendiente y no forma parte de la máquina de estados.
**Evidencia:** `tests/test_task_contracts.py` y `tests/test_state_machine.py` validan la matriz de campos, identidad, intentos, resultados, transiciones permitidas, rutas de revisión/reintento y terminalidad.

## D-009 — Identificador de modelo en historiales y compatibilidad heredada de lectura
**Fecha:** 2026-10-10
**Contexto:** los historiales confirmados en `HEAD` contienen `output`, `date` y `observations`, pero no `model`. En el árbol de trabajo, el operador añadió `model` a los 30 registros existentes y los prompts nuevos lo incorporan en historiales provisionales y adjudicados. `src/review_data_loader.py` asocia cada historial al modelo por su archivo y no valida ni consume campos internos, por lo que ambos formatos se pueden leer actualmente. Las revisiones principales y los perfiles usan un contrato distinto con `model_name`.
**Opciones:** exigir `model` retroactivamente y rechazar todo legado; inferir y reescribir historiales anteriores; mantener lectura transitoria del legado y exigir el contrato estricto solo para registros nuevos.
**Decisión:** todo historial provisional o adjudicado nuevo debe contener exactamente los campos contractuales `model`, `output`, `date` y `observations`, con `model` igual a `gemma`, `mistral` o `llama` y consistente con su archivo de destino. Un historial anterior sin `model` puede admitirse temporalmente solo en lectura cuando el modelo esté determinado inequívocamente por el nombre de archivo conocido o por un bloque de entrada explícito; no se modifica, completa ni usa como plantilla de salida. Una procedencia ambigua se rechaza o se señala para revisión. El contrato de revisión principal y las estructuras de perfiles no cambian: continúan usando `model_name`.
**Consecuencias:** los consumidores actuales permanecen compatibles sin migrar datos automáticamente. Un validador/escritor futuro deberá separar `legacy_read` de `strict_write`, impedir valores fuera de `gemma`, `mistral` y `llama`, y nunca sustituir `model_name` por `model` en revisiones o perfiles. La excepción heredada deberá retirarse únicamente después de una migración explícita, respaldada y verificada.
**Evidencia:** validación local con `jq` confirma 10 registros actuales por modelo, todos con los cuatro campos, valores permitidos y coincidencia archivo/modelo; `git show HEAD` confirma 30 registros heredados sin `model`; los tres perfiles reales y los 30 archivos de revisión conservan `model_name`; la inspección de `load_histories()` confirma lectura permisiva sin dependencia del campo nuevo.

## D-010 — Validación integral local antes de configurar la ejecución remota
**Fecha:** 2026-10-11
**Contexto:** D-007 separó el desarrollo local de la ejecución final remota, pero era necesario precisar dónde implementar y validar inicialmente el flujo completo de revisión y adjudicación antes de preparar accesos e infraestructura del servidor.
**Decisión:** toda implementación y prueba inicial del flujo Playwright se realiza en la Mac local. La puerta local comprende recopilación y alineación de declaraciones, outputs, perfiles e historiales; preparación de entradas; validación y recuperación de revisores; dependencias de adjudicación; y persistencia segura. Solo después de superar la validación local aplicable se configura la máquina remota, donde el flujo se valida nuevamente de forma independiente.
**Consecuencias:** las pruebas locales usan datos sintéticos o copias controladas y no requieren plataformas externas salvo autorización expresa; la lógica permanece portable; accesos, perfiles, credenciales y runtime remotos se aplazan; `LOCAL_TESTED` no implica `REMOTE_TESTED` y el estado inicial remoto es `REMOTE_NOT_CONFIGURED`.
**Evidencia:** alineación documental de `AGENTS.md`, `context/environments.md`, `context/deployment.md`, `context/workflow-review-adjudication.md` y el prompt activo de fase 2; no se ejecutó ni modificó infraestructura remota.

## D-011 — Identidad y resultado atómico de la revisión principal
**Fecha:** 2026-10-11
**Contexto:** la auditoría de 2.1 confirmó que una tarea `evaluation` podía omitir el revisor y que `TaskResult.success()` aceptaba resultados parciales. Eso permitía colisiones de deduplicación entre ChatGPT, Gemini y Grok y no garantizaba que una ejecución contuviera las siete salidas obligatorias de `main_review.md`.
**Opciones:** reemplazar los `TaskType` genéricos; depender de convenciones en `provider`, `metadata` y mapas JSON; conservar los tipos existentes y añadir una especialización mínima para la revisión principal.
**Decisión:** conservar `TaskType.EVALUATION` y añadir `ReviewOperation.MAIN_REVIEW`, `statement_index` y `Reviewer` como identidad conjunta obligatoria cuando una tarea representa una revisión. Añadir `CompleteReviewResult` y artefactos tipados para la revisión principal, tres historiales y tres propuestas de perfil, todos con procedencia de statement, revisor e intento. Solo un conjunto completo y consistente puede convertirse a `TaskResult` exitoso.
**Consecuencias:** las revisiones del mismo statement por revisores distintos tienen claves diferentes; los reintentos conservan tarea y clave, pero usan nuevos `attempt_id`; un artefacto faltante, duplicado, mal identificado o procedente de otro intento se rechaza antes de `COMPLETED`. `TaskResult` y los tipos genéricos existentes permanecen compatibles. No se modelaron adjudicaciones por rango, persistencia ni orquestación.
**Evidencia:** pruebas sintéticas de identidad y de las siete salidas, suite local completa, compilación Python y `pip check` ejecutados en macOS con Python 3.11.17; resultados detallados en `context/advances.md`.

## D-012 — Persistencia exclusiva en archivos para revisión y adjudicación
**Fecha:** 2026-10-11
**Contexto:** la planificación anterior de fase 2 proponía persistencia relacional, pero el flujo operativo real ya tiene archivos JSON/JSONL como artefactos y destinos verificables. El operador definió que estos archivos deben ser la fuente de verdad y que el estado debe poder reconstruirse sin infraestructura adicional.
**Opciones:** añadir almacenamiento relacional y sincronizarlo con los archivos; mantener un registro paralelo; usar exclusivamente los archivos reales con validación estructural, escrituras atómicas e idempotencia.
**Decisión:** el workflow de revisión y adjudicación usará exclusivamente archivos JSON/JSONL para estados, intentos y resultados. Selección del statement, recuperación, barrera, adjudicaciones, aplicación y completitud se determinan inspeccionando y validando esos archivos. No se implementará SQLite, SQL ni otra base de datos para este flujo. La construcción o filtrado de datasets y el entrenamiento o fine-tuning quedan fuera de su alcance.
**Consecuencias:** el siguiente entregable autorizado, después de aprobar 2.1, deberá centrarse en inspección por `statement_index`, validación estructural, prevención de duplicados, escrituras atómicas, reemplazo integral del revisor afectado, preservación de resultados válidos y distinción entre completitud de tarea y de statement. El valor genérico `TaskType.DATASET_PREPARATION` y módulos ajenos pueden conservarse por compatibilidad, pero no son una etapa activa ni una dependencia de este workflow. El nombre `data/finetuning/review_cases/` se conserva como ruta real sin implicar trabajo de entrenamiento.
**Sustituye:** toda planificación activa previa de almacenamiento relacional, WAL, migraciones o un entregable de base de datos para la fase 2. Las menciones anteriores en evidencias históricas se conservan como registro de lo que se había planificado y quedan explícitamente superadas por esta decisión. No sustituye D-008, D-009, D-010 ni D-011.
**Evidencia:** alineación documental de `AGENTS.md`, arquitectura, flujo operativo, prompt activo y registro de avances; no se modificaron código ni datos y las pruebas de código quedaron `NOT_RUN` por alcance.

## D-013 — Selección conservadora del statement y del run
**Fecha:** 2026-10-11
**Contexto:** 2.2.1 debe seleccionar secuencialmente un statement sin implementar todavía la completitud global, y los archivos reales contienen varios runs con rangos distintos. Elegir por orden alfabético, fecha o nombre podría mezclar entradas o adelantar el flujo sin evidencia.
**Opciones:** inferir la completitud desde archivos permanentes y tomar el run más reciente; reutilizar el cargador existente que selecciona el nombre máximo; recibir la completitud como dato externo y exigir selección inequívoca o explícita del run.
**Decisión:** el selector ordena los directorios reconocidos por índice numérico y recibe `CompletionState.COMPLETE`, `INCOMPLETE` o `UNKNOWN`. Solo `COMPLETE` permite proponer el índice siguiente; `INCOMPLETE` reanuda el último y `UNKNOWN` devuelve `pending`. El cargador acepta un run explícito o descubre candidatos por contenido; si hay cero o más de uno, devuelve un bloqueo estructurado y no selecciona. Los tres outputs siempre proceden del mismo directorio y cada `run_id` debe coincidir con él.
**Consecuencias:** 2.2.1 no crea directorios, no marca statements completos, no mezcla runs y no convierte la inspección en una tarea de revisión. El verificador global continúa reservado para 2.2.3. `src/review_data_loader.py` se conserva compatible y sin cambios, aunque su función histórica `get_latest_run()` no se usa para esta selección porque aplica una política no autorizada.
**Evidencia:** 17 pruebas sintéticas de selección, validación, ambigüedad y solo lectura; regresión local completa con 56 pruebas aprobadas, 3 smoke omitidas deliberadamente y 26 subpruebas aprobadas.

## D-014 — Integridad estricta y compatibilidad histórica en el inspector
**Fecha:** 2026-10-11
**Contexto:** `CompleteReviewResult` exige siete salidas de una misma ejecución, mientras que los casos históricos solo conservan las tres revisiones principales y `adjudication.json`. El repositorio no confirma nombres para los temporales ni conserva identificadores de tarea/intento en esos archivos.
**Opciones:** inferir nombres e identidad por ubicación; declarar incompleto todo caso sin temporales; aceptar como completo cualquier directorio con revisiones permanentes; separar validez estructural de procedencia y representar explícitamente la incertidumbre.
**Decisión:** el inspector recibe rutas temporales explícitas, valida contenido con los contratos de 2.1 y solo declara `COMPLETE` cuando los siete artefactos tienen procedencia común verificable. Faltantes activos producen `INCOMPLETE`, contradicciones o estructuras inválidas producen `INVALID`, ausencia total produce `NOT_STARTED` y un conjunto estructuralmente plausible sin evidencia común produce `UNVERIFIED`. Los casos históricos con adjudicación y temporales ausentes quedan `UNVERIFIED`, no incompletos ni completos.
**Consecuencias:** no se inventan nombres, intentos ni marcadores retroactivos. `INCOMPLETE` e `INVALID` recomiendan repetir íntegramente al revisor; `NOT_STARTED` recomienda su primera revisión; `UNVERIFIED` bloquea adjudicaciones hasta resolver la procedencia; `COMPLETE` conserva resultados. La barrera es informativa y no sustituye 2.2.3.
**Evidencia:** 18 pruebas sintéticas del inspector, 60 pruebas focalizadas con 26 subpruebas y suite local de 74 pruebas aprobadas; inspección real de `statement_000` confirmó tres estados históricos `UNVERIFIED` y adjudicación bloqueada sin modificar archivos.

## D-015 — Cierre histórico confirmado por el operador para statements 000–009
**Fecha:** 2026-10-11
**Contexto:** el inspector de 2.2.2 clasifica como `UNVERIFIED` los resultados históricos que no conservan temporales ni identificadores de ejecución. El operador confirmó explícitamente que `statement_000` a `statement_009`, ambos inclusive, ya fueron revisados y adjudicados, y que sus actualizaciones de perfiles e historiales se aplicaron manualmente.
**Opciones:** reconstruir metadatos inexistentes; repetir el procesamiento para generar evidencia nueva; confundir `UNVERIFIED` con trabajo pendiente; registrar la confirmación humana como una dimensión de cierre distinta de la verificación técnica automática.
**Decisión:** los diez statements forman un conjunto histórico finalizado por confirmación explícita del operador. Quedan excluidos de recuperación automática, nuevas revisiones, nuevas adjudicaciones y reaplicación de perfiles o historiales. No se les exigirán identificadores de ejecución ni temporales que no existían o ya fueron eliminados; sus archivos no se modificarán y no se inferirán metadatos retroactivos. La clasificación técnica `UNVERIFIED` puede conservarse como diagnóstico del inspector, pero no autoriza ninguna repetición.
**Consecuencias:** la completitud histórica confirmada y la completitud verificada automáticamente son dimensiones independientes. La primera establece el cierre operativo del rango `000`–`009`; la segunda continúa aplicándose a statements activos o futuros con evidencia técnica completa. El verificador global de 2.2.3 deberá respetar esta exclusión sin fabricar evidencia, pero no se implementa en esta decisión. D-014 conserva íntegro su significado técnico y queda complementada por esta política operativa.
**Evidencia:** confirmación explícita del operador registrada en esta tarea. No se reconstruyó evidencia técnica retroactiva ni se modificaron archivos de los statements, perfiles o historiales.

## D-016 — Completitud global por composición y evidencia local explícita
**Fecha:** 2026-10-11
**Contexto:** desde `statement_010`, los cuatro JSON permanentes no demuestran que las tres revisiones completas compartan procedencia ni que las adjudicaciones de historial y perfil se hayan aplicado una sola vez. Los archivos acumulados existentes describen estado, pero no vinculan por sí mismos ese estado con una ejecución concreta.
**Opciones:** inferir aplicación desde `outputs_reviewed` y presencia de historiales; declarar completo todo caso adjudicado; añadir una base de datos o registro general; componer los inspectores existentes y exigir una evidencia local mínima, explícita y verificable.
**Decisión:** 2.2.3 implementa un verificador determinista de solo lectura. D-015 resuelve `000`–`009` como `HISTORICAL_COMPLETE`; para índices nuevos, `COMPLETE` exige entradas, tres revisiones completas, adjudicación final válida, historiales y perfiles válidos, evidencia coherente de aplicación y limpieza confirmada. Faltantes o contradicciones demostrables son `INCOMPLETE`; falta de evidencia suficiente sin contradicción es `UNVERIFIED`.
**Contrato de evidencia:** una ruta explícita debe contener versión, statement, run, intentos de los tres revisores, hash canónico de la adjudicación final, identificadores y hashes de los tres historiales y tres perfiles aplicados, metadatos acumulados de perfil y confirmación de limpieza. El verificador no crea esta evidencia ni deduce su ubicación.
**Consecuencias:** `decision.status` no altera la completitud; el selector reutiliza `COMPLETE`, `INCOMPLETE` y `UNKNOWN` mediante un adaptador y no cambia su contrato. La futura etapa de escritura deberá emitir la evidencia atómica e idempotentemente después de aplicar y comprobar efectos. No se introducen SQL, ejecución de recuperación, adjudicaciones ni escrituras persistentes.
**Evidencia:** 30 pruebas sintéticas nuevas; revalidación focalizada de 2.1–2.2.3 con 90 pruebas y 26 subpruebas aprobadas; suite local con 104 pruebas aprobadas, 3 smoke de navegador omitidas deliberadamente y 26 subpruebas aprobadas. La inspección real de solo lectura clasificó `statement_010` como `INCOMPLETE` sin modificar archivos.

## D-017 — Conjuntos inmutables y referencia atómica para resultados de un revisor
**Fecha:** 2026-10-11
**Contexto:** siete reemplazos individuales con `os.replace()` pueden dejar visibles archivos de dos intentos si el proceso se interrumpe. A la vez, deben conservarse los nombres permanentes y la lectura histórica sin introducir una base de datos.
**Opciones:** sobrescribir siete rutas directamente; usar un manifiesto de estado junto a archivos mutables; publicar un directorio inmutable por intento y confirmar uno mediante una referencia atómica.
**Decisión:** cada `CompleteReviewResult` nuevo se prepara como un conjunto inmutable versionado por el hash de `task_id` y `attempt_id`. Un `manifest.json` vincula identidad, nombres y hashes de los siete JSON. Solo `active.json`, reemplazado atómicamente después de validar el conjunto, lo convierte en la versión confirmada. El nombre fijo de la revisión principal se conserva como proyección compatible, pero el inspector determina validez exclusivamente desde la referencia y el manifiesto cuando estos existen.
**Consecuencias:** no se afirma una transacción atómica de siete archivos. Una interrupción anterior al cambio de referencia deja vigente el conjunto previo; directorios preparados huérfanos no se aceptan. La misma identidad y contenido es idempotente; reutilizar identidad con contenido diferente se rechaza; otro intento reemplaza el conjunto como unidad lógica y conserva los demás revisores. Los históricos `000`–`009` se bloquean en el escritor. La limpieza de versiones huérfanas o antiguas no pertenece a 2.2.4-A.
**Evidencia:** 30 pruebas sintéticas del escritor; revalidación focalizada con 120 pruebas y 26 subpruebas aprobadas; suite local con 134 pruebas aprobadas, 3 smoke de navegador omitidas deliberadamente y 26 subpruebas aprobadas. Los fallos simulados de preparación y publicación conservaron la referencia anterior y el inspector rechazó alteraciones o mezclas.

## D-018 — Aplicación adjudicada preparada, verificable y no transaccional
**Fecha:** 2026-10-11
**Contexto:** `adjudication.json`, tres JSONL de historial y tres perfiles JSON son destinos separados. Reemplazarlos individualmente no crea una transacción multiarchivo, pero la persistencia debe impedir duplicados, detectar interrupciones y dejar datos suficientes para la evidencia global futura.
**Opciones:** sobrescribir directamente los siete destinos; afirmar completitud después de siete `os.replace()`; preparar una operación identificada con preimágenes, resultados objetivo y estado verificable, reservando evidencia y limpieza globales para 2.2.4-C.
**Decisión:** 2.2.4-B valida integralmente las siete salidas y crea una aplicación inmutable identificada por su contenido y procedencia disponible. Su manifiesto conserva hashes de origen/destino, adjudicación, historiales, perfiles, metadatos, run e intentos; `status.json` distingue preparación, aplicación y aplicación verificada. Cada archivo se reemplaza solo si aún coincide con su preimagen o ya contiene el resultado objetivo. La misma identidad es idempotente; una adjudicación, historial o aplicación diferente para el statement se rechaza. Los índices `000`–`009` permanecen bloqueados.
**Consecuencias:** una interrupción puede dejar algunos destinos aplicados, pero nunca se presenta como atomicidad o completitud global: el inspector devuelve `INTERRUPTED` hasta que la misma identidad termine y verifique los siete archivos. El manifiesto aporta a C los campos compatibles con el contrato de evidencia de 2.2.3, pero B no genera esa evidencia, no limpia temporales ni marca `COMPLETE`. Cambios concurrentes o aplicaciones competidoras se bloquean para evitar sobrescrituras silenciosas.
**Evidencia:** auditoría de consumidores y pruebas sintéticas de A; 28 pruebas de B, 151 pruebas focalizadas más 26 subpruebas y suite local con 165 pruebas aprobadas, 3 smoke de Chromium omitidas deliberadamente y 26 subpruebas aprobadas. No se escribieron datos reales ni se accedió a plataformas externas.

## D-019 — Recuperación por preimagen, evidencia final y limpieza explícita
**Fecha:** 2026-10-11
**Contexto:** una aplicación de B puede quedar preparada, parcialmente aplicada o aplicada sin evidencia. Además, los perfiles e historiales acumulados pueden avanzar con statements posteriores, y los artefactos confirmados de revisión no pueden eliminarse sin invalidar la inspección.
**Opciones:** volver a ejecutar adjudicaciones; sobrescribir destinos desde las copias preparadas; aceptar la evidencia como autoridad independiente; recuperar solo contra preimágenes verificadas, conservar conjuntos confirmados y limpiar exclusivamente rutas sueltas declaradas.
**Decisión:** C reanuda una aplicación únicamente cuando cada destino coincide con su preimagen o su objetivo registrados. Cualquier tercer hash bloquea la recuperación.
